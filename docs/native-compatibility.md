# Native compatibility evidence

Native deletion probes were run on 2026-11-08, macOS 15.7.4 arm64, with Codex CLI **0.167.0** and Claude Code **2.1.319**. Those deletion probes used disposable synthetic data roots. No existing user session was deleted or rewritten, and no model turn was requested during deletion verification. These versions describe the scope of the historical native evidence. The current Codex deletion adapter checks required CLI capabilities instead of an exact version. Its updated invocation and history-index recovery have not been exercised through native deletion or resume probes.

## History slimming: synthetic checks and limited native resume

The deletion evidence below does **not** validate resuming rewritten history. `slim-history` uses recognized record structures rather than a client-version allowlist. In-memory JSONL and SQLite tests cover untouched bytes, image placeholders, successful shell output, direct reasoning ciphertext removal, byte-offset remapping, cached items, ordinals, commit/rollback, receipt hashes, malformed-input rejection and idempotence. Reasoning-only and combined operations both exercise index updates using in-memory SQLite. Pure metadata and UI tests cover the strict 72-hour cutoff, excluding protected savings, combined category totals and explicit confirmation. Synthetic filesystem fixtures check plain/zstd headers, ownership and references without invoking the planner, executor or native clients.

Read-only inspection on 2026-11-09 found matching Claude image and tool-result shapes across 27 local 2.1.x versions. Codex headers included 0.154.0, 0.163.0, 0.165.0, 0.166.0 and 0.167.0. Version numbers are metadata, not a reliable format boundary. Synthetic tests include old, newer, custom and absent version values, plus Claude sessions continued across upgrades. Existing version fields are preserved unchanged; malformed identities and unsupported reference layouts remain blocked. Inspection did not rewrite real history or estimate savings.

Analysis does not mark a file incomplete solely because its version fields differ. Claude whole-session deletion also uses structure and verified ownership rather than a version gate. This broader structural support does not extend the native probe evidence beyond the versions and fixtures documented below.

A separately authorized experiment on 2026-11-09 copied one completed real Codex session created with CLI **0.166.0** and resumed both original and stripped copies using **0.167.0**, **gpt-6-astra** and the same OpenAI provider. Removing one direct reasoning `encrypted_content` field reduced the file from **345,181 to 339,106 bytes** (6,075 bytes); every other byte was preserved. Both variants restored the same two visible turns, completed a real model continuation with the same correct recall result, and reopened after restart with three turns. The source file's hash and modification time were unchanged; temporary authentication copies were removed.

That experiment rebuilt **fresh isolated SQLite indexes**. It did not exercise this application's in-place rewrite of existing SQLite offsets, an interrupted native recovery, complex tool chains, active turns, compaction, other accounts/models or image/output slimming. It was not a speed, cost or reasoning-quality benchmark. The current existing-index rewrite and recovery guards have synthetic coverage only; no further native probes were run while adding this operation.

Images, omitted output and removed encrypted reasoning state are permanently lost after a successful operation; transaction recovery is not undo. Keeping identities and signed fields unchanged does not by itself prove native replay compatibility for other histories.

Codex supports independent plain legacy and paginated histories. The [history materializer](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/thread-store/src/local/thread_history_materialization.rs) and [turn-position schema](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/state/thread_history_migrations/0003_turn_rollout_positions.sql) persist byte positions. The implementation remaps known `thread_history_projection_state` and `thread_turns` offsets to rewritten UTF-8 line boundaries, and slims recognized canonical event items and `thread_items` / `thread_realtime_items` JSON caches. Ordinals, root-turn IDs and unrelated rows are preserved. Unknown offset schemas or update triggers are rejected; the native delete-only cache cleanup trigger is accepted.

Every Codex history rewrite requires an explicit `codexProjection` receipt, including an empty array when no history databases exist. Execution and interruption recovery reject a missing receipt; generic delete/compress actions cannot modify session files. Finalized historical receipts remain readable. Database identities, schemas and target rows are bound to preview hashes. SQLite write transactions stay open across the atomic JSONL replacement. The original is retained until index commits verify; interruption recovery accepts already-updated indexes and completes pending updates from the verified original. Conflicting state retains the backup for review. This mechanism completes an interrupted operation; it does not provide undo after successful finalization.

All current and archived headers, including `.jsonl.zst`, are inspected for inbound [history-lineage references](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/thread-store/src/local/rollout_lineage.rs). Shared, forked, imported, attached, compressed or hardlinked targets and referenced sources are retained. Unrelated compressed/hardlinked histories no longer block an independent target. Incomplete inventories, unreadable headers and unrecognized reference identities still prevent establishing dependency coverage. Compressed targets are inspected but not rewritten.

Codex configuration is parsed as TOML, including quoted/escaped keys and multiline strings. The root `sqlite_home` takes precedence over trimmed `CODEX_SQLITE_HOME`, matching the [native configuration resolver](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/config/mod.rs). Both can point to the scanned root; external databases are outside the verified inventory. Invalid or changed configuration and relative environment paths with an unknown native working directory cannot establish index coverage. Synthetic tests cover these cases and ensure parser errors do not expose configuration values.

Reasoning removal only deletes a nonempty string `encrypted_content` member from direct `response_item` reasoning records. It preserves summaries/content, IDs, signatures, compaction ciphertext, nested replacement histories, Claude thinking and all untouched raw bytes. Known SQLite reasoning items store visible summaries/content and remain unchanged; their containing turn offsets still move when the rollout shrinks. `state_*.sqlite` identity/path/timestamp metadata is unaffected by this content-only rewrite; whole-session deletion remains on the native coordination path described below.

The in-memory history transformer has a 64 MiB per-file resource bound; configuration inspection has a 64 KiB bound. These are implementation limits, not provider-version restrictions. Claude files must have consistent session identity. Compacted replacement histories and unrecognized image shapes are left untouched.
## Codex native deletion: capabilities and historical 0.167.0 evidence

`src/codex-delete.ts` invokes `codex --no-daemon -c ... delete <uuid> --force` with an argument array. It accepts a full hexadecimal UUID only, requires a canonical absolute directory, fixes `CODEX_HOME`, `CODEX_SQLITE_HOME`, `sqlite_home` and `log_dir`, and runs with that directory as its working directory. Before deletion, `delete --help` must advertise the session argument, force and config options, and `features list` must confirm both background history maintenance features are disabled under the same overrides. Root identity is rechecked between commands. The version string is informational. Native deletion has no shell evaluation, session-name lookup, direct SQLite mutation, or fallback that unlinks rollouts after a native failure.

The tagged command is a thin app-server client. The current adapter explicitly passes `--no-daemon` and rejects inherited `CODEX_EXEC_SERVER_URL` and `CODEX_EXEC_SERVER_NOISE_*` selection. It disables `features.local_thread_store_compression` and `features.background_paginated_rollout_migration` for this invocation, because native startup can otherwise rewrite unrelated rollouts. Configuration may still cause ordinary native startup behavior; this adapter does not promise an entirely network-free child process. Passing capability checks does not establish native compatibility for every version.

Runtime overrides supersede ordinary system, cloud, user, and project configuration. Legacy managed configuration can override them. The adapter conservatively refuses deletion when `/etc/codex/requirements.toml` or `/etc/codex/managed_config.toml` exists, when their absence cannot be established, or when macOS reports a forced `config_toml_base64` / `requirements_toml_base64` preference for `com.openai.codex`. The macOS check queries only the two CoreFoundation presence flags, without copying, decoding, or displaying configuration values. No management policy is removed or bypassed.

Native startup can write outside the selected rollout. Before launching deletion, the adapter checks the root SQLite files and sidecars, `skills/.system`, `tmp`, `.tmp`, `log`, `logs`, `thread-writer-locks`, `sessions`, `archived_sessions`, `installation_id`, `session_index.jsonl`, and `session_index.jsonl.lock`. Symlinks, special files and hardlinks in native maintenance paths are rejected. History hardlinks are checked against the selected ownership scope, so unrelated histories remain usable. The `skills` ancestor is also checked. Ordinary user skill and plugin links outside those paths are allowed. One narrow exception permits native executable aliases at `tmp/arg0-{macos,linux}/codex-arg0*/{apply_patch,applypatch,codex-linux-sandbox}`; those leaf links are not traversed, and native stale-directory cleanup unlinks them. Linked ancestors and lock files remain rejected.

Each child command has a 15-second deadline and a combined 64 KiB output bound. On supported POSIX execution the entire child process group is killed, including a descendant retaining its parent's output pipe. Native stdout/stderr is never included in failure messages. A timeout or error requires reconciliation; it must not trigger an automatic retry or a success receipt.

### Reproducible native integration test

This test executes native deletion against disposable fixtures. Run it only when explicitly requested; development authorization alone does not authorize cleanup tests (see `AGENTS.md`).

```sh
node --disable-warning=ExperimentalWarning --test test/codex-delete.test.ts
```

The installed-CLI test skips when Codex is absent or has another version. It creates five minimal synthetic rollout files: a parent, its child, a grandchild, an archived child, and an unrelated survivor. `codex app-server --listen stdio://` receives only `initialize`, `thread/list`, and `thread/read`; it initializes the synthetic indexes without a model prompt. Read-only SQLite inspection verifies three spawn edges before deletion.

The historical probe removed the parent, child, grandchild, and archived child JSONL files, their four `threads` rows, and their three `thread_spawn_edges` rows. The unrelated session remained in the native list and its `thread/read` turns were unchanged and nonempty. This proves transitive **spawn** descendants and archived spawn descendants for that fixture and invocation. It does not prove that every possible Codex attachment or auxiliary resource is deleted, or validate the updated adapter invocation.

A separate synthetic probe with an attached relationship present only in the database found that its row and rollout survived deletion of the parent. Tagged source additionally checks attached relationships in rollout metadata and rejects parent deletion while such attached children exist. Therefore `attached_thread_parent_id` must not be treated as a spawn edge, and absence from `thread/list` alone is insufficient deletion proof. The planner refuses affected attached relationships.

Tagged deletion source removes every discovered rollout for the selected stable session IDs, including each plain `.jsonl` and its `.jsonl.zst` sibling. It also removes their materialized `thread_history_1.sqlite` entries, selected agent message boards in `agent_message_board_1.sqlite`, and their `session_index.jsonl` names before the final state-row deletion. The planner inspects plain and compressed headers, rejects unpreviewed rollouts belonging to selected sessions, and checks inbound references through stable and immutable IDs. Unrelated compressed/hardlinked histories are allowed; compressed siblings are never silently added to the deletion set. These auxiliary cleanup details are source evidence, not a claim that arbitrary attachments were exercised by the minimal fixture.

### Shared writes and accounting

Observed native startup writes included `state_5.sqlite`, `goals_1.sqlite`, `logs_2.sqlite`, `memories_1.sqlite`, `queue_1.sqlite`, their SQLite WAL/SHM files, `installation_id`, bundled `skills/.system` files, `tmp/arg0-macos` aliases/locks, `.tmp/plugins.sync.lock`, `.tmp/git-*`, and `thread-writer-locks/.coordination.lock`. Log output is pinned below the selected root. This startup overhead can exceed the bytes removed from a small synthetic conversation. Removing SQLite rows does not imply that the database file shrinks; cc-clean does not run `VACUUM`.

The executor compares complete pre/post root snapshots, includes native-created files as signed overhead, verifies planned rollout absence and index-row absence, and checks for external activity before and after the native command. Selected rollout fingerprints alone do not bind the native deletion set: SQLite/WAL spawn edges can change without those files changing. Planning recomputes each action's exact spawn closure from the freshly read index, checks files and parent/archive relationships against analysis, and execution repeats the closure check. Unknown/unindexed descendants and omitted selected sessions prevent mutation.

After deletion, the remaining index IDs and exposed path/project/parent/attachment/time/archive metadata must be unchanged. There must be no new thread. Non-target file fingerprints and links must be unchanged except for known native maintenance paths: numeric versions of the state/logs/goals/memories/queue/thread_history/agent_message_board SQLite families and their sidecars, session name index/lock, installation ID, bundled system skills, native arg0 temporary directories, pinned log directory, thread-writer locks, `.tmp/plugins.sync.lock`, and `.tmp/git-*`. An unexpected change leaves `needs-review` and no credited reduction. This check does not compare every internal SQLite column or prove the absence of a same-metadata filesystem race. The caller still requires complete deep analysis for native deletion; unrelated malformed or over-limit transcripts can prevent establishing the full session graph.

Filesystem checks and graph checks are observations, not an operating-system transaction. Another process can change a directory, link, file, or database between checks and launch. Activity detection, immediate revalidation, and postchecks reduce that race; ambiguous or unexpected results remain `needs-review`. Minimal synthetic fixtures do not establish cleanup semantics for arbitrary images, goals, history entries, worktrees, or future record types; retained resources remain measured separately.

### Session-created temporary outputs

`src/session-temp.ts` adds evidence-based discovery to Quick clean, ordinary CLI `clean`, **Clean temporary files**, and `clean --temp-only`. Layout evidence comes from completed Codex `item_completed` command/file-change events, correlated legacy Codex shell calls/results, and Claude Bash calls/results. These are format checks, not version gates. Commands are never re-executed. Paths are taken from successful outputs of bounded `mktemp -d` forms or standalone Python allocation/print scripts, and from bounded `mkdir` command prefixes. `mkdir` directories and completed Codex file additions qualify only under standard system temp roots. `$TMPDIR`, `$TMP`, `$TEMP`, `$CLAUDE_CODE_TMPDIR`, brace variants, expanded paths and macOS `/private` aliases are handled without evaluating shell expressions or using the current environment. Verified `mktemp`/Python directory creation can identify custom locations outside the current temp environment.

The `mkdir` grammar recognizes literal temporary-path assignments, absolute `cd`, temporary-path `rm -rf` / `rm -fr`, and `mkdir` / `/bin/mkdir` with optional `-p` and `--`. Statements may use `&&`, semicolons or newlines; variables resolve only from earlier assignments in the same command, respecting single quotes. Unknown syntax ends prefix recognition. Shell-control variable assignments, unresolved expansions, substitutions, globs, traversal, conditional blocks and unsupported operators do not establish creation. Only successful completed results qualify; explicit Claude background-task and interruption metadata, and background-start output, are rejected.

The rule source includes local Claude Bash histories inspected read-only on 2026-11-09: literal `mkdir -p /tmp/<directory>` and `E=/tmp/<directory> && rm -rf $E && mkdir -p $E && ...` chains used for test outputs and source exports. The updated collector matched two export-directory roots and two nested output directories to their filesystem birth times. A failed compound command and paths without a supported successful creation record did not qualify. This validates historical command recognition and metadata association, not cleanup eligibility or comprehensive discovery.

The Python grammar allows only `tempfile`/`pathlib`/`os` imports, one `tempfile.mkdtemp(prefix=...)` assignment (optionally wrapped in `pathlib.Path`), optional `os.chmod(variable, 0o700)`, and `print(variable)`. Arbitrary Python, including creation mixed with file-writing or subprocess calls, is unsupported. This deliberately does not claim comprehensive discovery of all AI-generated temporary files.

Evidence binds provider, history, session/tool identity, creation interval, filesystem birth time and object identity. Histories must be ordinary safely owned JSONL files in the configured providers' session layouts. Inventory fingerprints are rechecked; inherited histories cannot prove creation, but references from them still retain targets. Other-history references in either provider, including basename/variable aliases, retain the scope. Incomplete, compressed, linked or changing history inventories fail closed. Only allowlisted text outputs qualify; repository ancestors and nested repositories, source/config/scratchpad paths, images, code and hidden files are protected. Recognized project markers (`package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`, `CMakeLists.txt`, and Gradle build/settings files) also retain exported source trees without `.git`; this is a bounded marker list, not detection of every source-project format. A protected nested repository may conservatively retain the entire scope. Temporary output execution precedes history rewriting so creation evidence remains valid.

Synthetic tests cover success/result correlation, duplicate identities, literal/variable/multiple-operand `mkdir` commands, rejected shell control flow and expansions, background/interrupted results, rejected Python text/rebinding, file additions, birth-time/identity mismatches, aliases, references across providers, unsafe/incomplete histories, repository and exported-project protection, cancellation, strict age checks, both-provider activity protection, inert receipt validation, menu cancellation and aggregated estimates. No cleanup planner, preview, executor, recovery path or native client was invoked for these checks. Actual execution/recovery and arbitrary historical script coverage remain unverified; no real temporary files were cleaned during development.

## Codex compressed history read support

Analysis recognizes current and archived `.jsonl.zst` histories and streams decoded records through the same parser as plain JSONL. Synthetic read-only fixtures cover Unicode records split across concatenated zstd frames, empty frames, compressed input larger than the read buffer, plain-path SQLite indexes, identity mismatches, token/date/model aggregation, cache reuse, decoded metadata sampling, cancellation, and damaged/truncated/trailing-invalid frames. Incomplete results are not cached as verified. File fingerprints are checked before and after reading; no uncompressed history file is created.

Disk, session and project sizes count stored bytes; parsing progress also uses stored bytes. Record/field/image analysis measures decoded content, and field/record percentages use decoded history bytes. These values must not be treated as cleanup savings. A same-basename plain file takes precedence for usage, while both physical files remain in storage totals. Its compressed sibling is not compared for equivalence and keeps the session incomplete for cleanup. A malformed plain file does not silently fall back to potentially stale compressed usage. Other paths claiming the same session identity still invalidate aggregate usage.

The pinned [Codex 0.167.0 compression source](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/rollout/src/compression.rs) publishes and verifies compressed output before removing the plain source. Append materialization recreates the plain file and removes the compressed file. Existing plain files take precedence, and compression skips an already-existing compressed sibling; therefore coexisting files need not be equal. This is source evidence, not a new native compression/resume probe or a guarantee for all Codex versions.

Compressed rewriting remains unsupported, and compressed histories still cannot prove session-created temporary-file ownership. Analysis itself never removes duplicates. No cleanup planner, preview, executor, native probe or real-history mutation was run for these checks.

## Claude request archives and hooks: limited native continuation evidence

A separately authorized experiment on 2026-11-09 copied one real transcript written by Claude Code **2.1.300** into four isolated data roots. Claude Code **2.1.319**, the existing configured provider and **claude-opus-5-5** completed a real continuation for each variant. Tools and live customizations were disabled with `--tools ''`, `--safe-mode`, `--strict-mcp-config` and empty setting sources; stored prompt snapshots remained enabled. No original history, cleanup planner, preview or executor was modified or invoked.

| Isolated variant | Bytes before continuation | Reduction | Exact historical recall | Reopened after continuation |
| --- | ---: | ---: | --- | --- |
| Original copy | 476,467 | 0% | Passed | Passed |
| Remove all three API request record types | 363,543 | 23.70% | Passed | Passed |
| Also clear hook `command` strings | 354,215 | 25.66% | Passed | Passed |
| Instead clear hook output and rendered context | 343,578 | 27.89% | Passed | Passed |

Request removal covered `api-request`, `api-request-shape` and `api-request-blob` together, avoiding stale audit references. The command variant cleared only the five `hook_success.attachment.command` strings and preserved every other retained byte. The output variant cleared `content`, `stdout`, `stderr` and recorded `rendered` content on the same five attachments, retaining their identities and parent links. It retained the command strings. Neither variant deleted whole hook rows or changed the UUID graph.

Each model response reproduced the earliest human message on the resumed branch exactly; an abandoned branch contained a near-duplicate message and was excluded from that recall criterion. All original user/assistant records, including thinking/signatures and usage, and both original `cost-state` records remained unchanged. Each variant appended a new response and cost record. Native terminal resume after process restart displayed the latest original user message and the new response. The source SHA-256 (`8045325a0c90f6018f5732c91ebafcb9bfd821376b64c19cc7f5727fbd312758`) and modification time were unchanged.

The baseline and request-only variants each reported 15,100 input tokens including cache reads/writes. Clearing hook output reduced that to 13,241, demonstrating actual loss of model-facing context; clearing only commands reported 15,105, with the same historical hook content retained. The four CLI-reported incremental costs totaled approximately **USD 0.1422**. These sequential calls had different cache hits and isolated working-directory paths, so they are not a cost, latency or context-equivalence benchmark, nor a provider-billing reconciliation.

Read-only inventory of 496 unique histories older than 72 hours found **329.1 MiB** of request blobs (**386.7 MiB** including shapes and request records), and **282.3 MiB** of `hook_success` rows. Serialized hook `command` values accounted for approximately **224.9 MiB**, or **79.7%** of hook-row bytes. Most hook rows were `PreToolUse` / `PostToolUse` with empty `content` and no recorded `rendered` context. This supports targeting request archives and repeated hook commands; the selected hook policy also clears successful-hook output and injected context, accepting that loss on resume. These are inventory/field measurements, not eligible cleanup savings: open-session protection was not evaluated, and structural envelopes must remain.

The tested tradeoff loses exact historical API request reconstruction and, when commands are cleared, the recorded hook implementation. Clearing hook output additionally loses historical instructions that the current environment may not reproduce. Continued use creates new request records. This request-archive experiment tested command-only and output/context-only clearing as separate variants. The separate [tool/skill experiment](#claude-tool-and-skill-snapshots-limited-native-continuation-evidence) also tested clearing hook commands and output together on another copied transcript, alongside tool/skill slimming, with successful continuation and a Read call. Evidence remains limited to these small transcripts and one client/provider/model setup; complex tool chains, compaction, other versions and arbitrary hook schemas remain unverified.

The implementation now includes both Claude operations in Quick clean, with separate unchecked choices in Slim history and explicit `--remove-request-archives` / `--compact-hooks` CLI flags. Archive removal deletes the complete recognized family only when independent conversation records exist; any unknown archive type or top-level field preserves the family. Hook compaction clears commands and output/context together only on recognized successful attachments, retaining their row identities, parent links, timestamps, execution metadata and untouched bytes. Unknown/failed hooks and unrelated prompt attachments remain intact. Both operations use the existing age/activity guards, estimates, atomic replacement and recovery path.

Synthetic tests cover each operation separately and together, combination with image/output slimming, exact category byte totals, raw cost/usage and signature preservation, UUID parent links, CRLF/LF and absent final newlines, malformed/unknown schemas, idempotence, receipt validation and provider-specific UI/CLI choices. The later combined-hook native evidence is described above; it does not exercise production cleanup execution or recovery. No cleanup planner, preview or executor was run during implementation or these continuation experiments.


## Claude tool and skill snapshots: limited native continuation evidence

Read-only inspection on 2026-11-09 compared one transcript written by Claude Code **2.1.296** with the embedded JavaScript in the installed **2.1.319** native executable. The transcript contains 51 records and 330,118 bytes; 26 attachment records account for 314,678 bytes (95.3%). Most of this is prompt/tool snapshots, skill listings and hook context. Inventory totals alone do not establish safe savings.

The [official CLI reference](https://code.claude.com/docs/en/cli-reference) documents that the recorded system prompt is reused across requests, including resume/continue, until compaction; `--system-prompt-snapshot off` instead rebuilds it. The inspected reader selects the latest valid `prompt_snapshot`, restores its system prompt and builds tool-description and tool-schema maps. Repeated descriptions in different fields therefore have distinct consumers. Removing or invalidating the snapshot can fall back to a live prompt, but that changes the replayed context. This static fallback is not proof that an edited transcript completes a native model turn.

Recorded `rendered` content is also used to replay model-facing messages. Without it, the client can reconstruct content from the attachment using its current rendering rules. It is not merely a duplicate display field. The empty display renderer for `prompt_snapshot` does not make it unused: prompt and tool replay consume it separately. Instructions, skill listings and hook output may also contribute context.
