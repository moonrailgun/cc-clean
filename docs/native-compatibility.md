# Native compatibility evidence

Native deletion probes were run on 2026-11-08, macOS 15.7.4 arm64, with Codex CLI **0.167.0** and Claude Code **2.1.319**. Those deletion probes used disposable synthetic data roots. No existing user session was deleted or rewritten, and no model turn was requested during deletion verification. These versions describe the scope of the historical native evidence. The current Codex deletion adapter checks required CLI capabilities instead of an exact version. Its updated invocation and history-index recovery have not been exercised through native deletion or resume probes.

## History slimming: synthetic checks and limited native resume

The deletion evidence below does **not** validate resuming rewritten history. `slim-history` uses recognized record structures rather than a client-version allowlist. In-memory JSONL and SQLite tests cover untouched bytes, image placeholders, successful shell output, direct reasoning ciphertext removal, byte-offset remapping, cached items, ordinals, commit/rollback, receipt hashes, malformed-input rejection and idempotence. Reasoning-only and combined operations both exercise index updates using in-memory SQLite. Pure metadata and UI tests cover the strict 72-hour cutoff, excluding protected savings, combined category totals and explicit confirmation. Synthetic filesystem fixtures check plain/zstd headers, ownership and references without invoking the planner, executor or native clients.

Codex image removal also recognizes inline `input_image` blocks in the structured `output` arrays of `function_call_output` and `custom_tool_call_output` response items. It requires a call identity and preserves explicitly failed, running or error results. Text quoting data URLs, remote URLs, file references, unknown blocks and nested compaction snapshots remain untouched. Synthetic plain/zstd tests cover mixed output, exact surrounding bytes, decoded SQLite offsets, unchanged cached tool text and recovery hashes. Opaque MCP result metadata, including screenshot URLs, is preserved. This added image format has not undergone native continuation validation.

Read-only inspection on 2026-11-09 found matching Claude image and tool-result shapes across 27 local 2.1.x versions. Codex headers included 0.154.0, 0.163.0, 0.165.0, 0.166.0 and 0.167.0. Version numbers are metadata, not a reliable format boundary. Synthetic tests include old, newer, custom and absent version values, plus Claude sessions continued across upgrades. Existing version fields are preserved unchanged; malformed identities and unsupported reference layouts remain blocked. Inspection did not rewrite real history or estimate savings.

Analysis does not mark a file incomplete solely because its version fields differ. Claude whole-session deletion also uses structure and verified ownership rather than a version gate. This broader structural support does not extend the native probe evidence beyond the versions and fixtures documented below.

A separately authorized experiment on 2026-11-09 copied one completed real Codex session created with CLI **0.166.0** and resumed both original and stripped copies using **0.167.0**, **gpt-6-astra** and the same OpenAI provider. Removing one direct reasoning `encrypted_content` field reduced the file from **345,181 to 339,106 bytes** (6,075 bytes); every other byte was preserved. Both variants restored the same two visible turns, completed a real model continuation with the same correct recall result, and reopened after restart with three turns. The source file's hash and modification time were unchanged; temporary authentication copies were removed.

That experiment rebuilt **fresh isolated SQLite indexes**. It did not exercise this application's in-place rewrite of existing SQLite offsets, an interrupted native recovery, complex tool chains, active turns, compaction, other accounts/models or image/output slimming. It was not a speed, cost or reasoning-quality benchmark. The current existing-index rewrite and recovery guards have synthetic coverage only; no further native probes were run while adding this operation.

Images, omitted output and removed encrypted reasoning state are permanently lost after a successful operation; transaction recovery is not undo. Keeping identities and signed fields unchanged does not by itself prove native replay compatibility for other histories.

Codex supports independent plain or zstd legacy and paginated histories. The [history materializer](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/thread-store/src/local/thread_history_materialization.rs) and [turn-position schema](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/state/thread_history_migrations/0003_turn_rollout_positions.sql) persist byte positions. The implementation remaps known `thread_history_projection_state` and `thread_turns` offsets to rewritten UTF-8 line boundaries, and slims recognized canonical event items and `thread_items` / `thread_realtime_items` JSON caches. Ordinals, root-turn IDs and unrelated rows are preserved. Unknown offset schemas or update triggers are rejected; the native delete-only cache cleanup trigger is accepted.

Every Codex history rewrite requires an explicit `codexProjection` receipt, including an empty array when no history databases exist. Execution and interruption recovery reject a missing receipt; generic delete/compress actions cannot modify session files. Finalized historical receipts remain readable. Database identities, schemas and target rows are bound to preview hashes. SQLite write transactions stay open across the atomic JSONL replacement. The original is retained until index commits verify; interruption recovery accepts already-updated indexes and completes pending updates from the verified original. Conflicting state retains the backup for review. This mechanism completes an interrupted operation; it does not provide undo after successful finalization.

All current and archived headers, including `.jsonl.zst`, are inspected for inbound [history-lineage references](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/thread-store/src/local/rollout_lineage.rs). Actual cross-rollout references, forked, imported and attached targets, referenced sources and independent identity copies are retained. Fully accounted hardlinks across supported Codex/Orca homes use the coordinated protocol below; other linked targets remain protected. Unrelated compressed/hardlinked histories no longer block an independent target. Incomplete inventories, unreadable headers and unrecognized reference identities still prevent establishing dependency coverage.

Header inspection streams across concatenated zstd frames, including empty frames and UTF-8 or newline boundaries, with a combined 1 MiB decoded header limit. It stops at the first complete line; validating the rest of the compressed history remains the full decoder's responsibility. Synthetic header/layout fixtures cover these boundaries, damaged input before the header completes, cancellation and preservation of inbound references without blocking independent histories. They do not establish native resume or cleanup execution compatibility.

Codex configuration is parsed as TOML, including quoted/escaped keys and multiline strings. The root `sqlite_home` takes precedence over trimmed `CODEX_SQLITE_HOME`, matching the [native configuration resolver](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/config/mod.rs). Both can point to the scanned root; external databases are outside the verified inventory. Invalid or changed configuration and relative environment paths with an unknown native working directory cannot establish index coverage. Synthetic tests cover these cases and ensure parser errors do not expose configuration values.

Reasoning removal only deletes a nonempty string `encrypted_content` member from direct `response_item` reasoning records. It preserves summaries/content, IDs, signatures, compaction ciphertext, nested replacement histories, Claude thinking and all untouched raw bytes. Known SQLite reasoning items store visible summaries/content and remain unchanged; their containing turn offsets still move when the rollout shrinks. `state_*.sqlite` identity/path/timestamp metadata is unaffected by this content-only rewrite; whole-session deletion remains on the native coordination path described below.

The in-memory history transformer accepts Claude files up to 64 MiB and Codex files up to 512 MiB stored and decoded, with a 64 MiB limit per JSONL line. Configuration inspection has a 64 KiB bound. These are implementation limits, not provider-version restrictions. Claude files must have consistent session identity. Compacted replacement histories and unrecognized image shapes are left untouched by image/output/reasoning operations.

## Codex compressed history read support

Analysis recognizes current and archived `.jsonl.zst` histories and streams decoded records through the same parser as plain JSONL. Synthetic read-only fixtures cover Unicode records split across concatenated zstd frames, empty frames, compressed input larger than the read buffer, plain-path SQLite indexes, identity mismatches, token/date/model aggregation, cache reuse, decoded metadata sampling, cancellation, and damaged/truncated/trailing-invalid frames. Incomplete results are not cached as verified. File fingerprints are checked before and after reading; no uncompressed history file is created.

Disk, session and project sizes count stored bytes; parsing progress also uses stored bytes. Record/field/image analysis measures decoded content, and field/record percentages use decoded history bytes. These values must not be treated as cleanup savings. A same-basename plain file takes precedence for usage, while both physical files remain in storage totals. Its compressed sibling is not compared for equivalence and keeps the session incomplete for cleanup. A malformed plain file does not silently fall back to potentially stale compressed usage. Other paths claiming the same session identity still invalidate aggregate usage.

The pinned [Codex 0.167.0 compression source](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/rollout/src/compression.rs) publishes and verifies compressed output before removing the plain source. Append materialization recreates the plain file and removes the compressed file. Existing plain files take precedence, and compression skips an already-existing compressed sibling; therefore coexisting files need not be equal. This is source evidence, not a new native compression/resume probe or a guarantee for all Codex versions.

Compressed histories still cannot prove session-created temporary-file ownership. Analysis itself never removes duplicates. No cleanup planner, preview, executor, native probe or real-history mutation was run for these checks.

## Codex compressed and larger history slimming

Independent `.jsonl.zst` histories use the same recognized transformations and protections as plain JSONL. Every concatenated zstd frame is decoded and validated before transformation; damaged, truncated or trailing invalid data retains the file. The [native seekable reader](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/rollout/src/seekable_reader.rs) defines offsets in original JSONL bytes regardless of storage encoding. SQLite projection updates therefore use decoded input/output, while preview hashes, staged replacements, backups and receipt sizes use stored bytes. Interrupted recovery decodes verified backups using the original history filename, including extensionless transaction backups. Coordinated hardlinks follow the same protocol across every discovered home.

The output is recompressed with Node's built-in zstd at level 3. Total estimated savings equal the stored input size minus the recompressed output size. Per-operation amounts are proportional allocations of that total, based on decoded byte reductions; they sum exactly to the total but do not measure each operation's independent compression effect. Files whose recompressed output does not shrink are retained with zero counts and savings. Same-basename plain/zstd pairs are excluded from slimming; after a separately confirmed duplicate cleanup, the remaining compressed history can be slimmed on a later run. Duplicate verification keeps its separate 64 MiB bound.

Codex slimming is bounded to 512 MiB for both stored and decoded content and 64 MiB per JSONL line. Larger inputs are retained. Processing remains in memory and may hold several large buffers at once; it is not a streaming rewrite. Unchanged JSONL bytes, line endings and large integer literals are preserved.

Synthetic tests cover plain and compressed histories above 64 MiB, concatenated/empty frames, Unicode split across frames, exact untouched bytes, corrupt input, size bounds, cancellation, no-growth recompression, stored category totals and unsafe old snapshots. In-memory SQLite tests cover decoded offsets and caches through mixed commit states; disposable layout and receipt fixtures cover compressed hardlinks and mandatory projection lifecycle. These checks do not invoke cleanup planning, preview, execution, recovery or native clients. Actual compressed cleanup, interrupted recovery and native continuation after this rewrite remain unverified end to end.

## Codex duplicate history cleanup

Ordinary Codex clean and Quick clean can remove the plain member of a same-basename `.jsonl` / `.jsonl.zst` pair in current or archived sessions. Every compressed frame must decode successfully, and the complete decoded bytes must equal the plain file. The compressed file is retained unchanged, preserving all conversation, usage and context bytes. Each stored file and the decoded result are bounded to 64 MiB. Different contents, malformed/truncated/trailing-invalid frames, additional independent identity copies, shared references, symlinks, unaccounted hardlinks, unknown history modes and unknown index dependencies retain the pair. Fully accounted hardlinks use the coordinated protocol below. Both files and all aliases must be strictly older than 72 hours and inactive; explicitly selecting the plain file does not exempt the pair.

The pinned [native compression implementation](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/rollout/src/compression.rs) resolves a logical plain rollout path through its compressed sibling. Since decoded bytes do not change, SQLite byte offsets, ordinals and cached content remain unchanged. Duplicate cleanup still validates the known projection schemas and hashes, holds their write transactions across the plaintext rename, and records mandatory `codexProjection` entries (including an explicit empty array). The existing transaction mechanism retains the plain original until final verification; interrupted recovery checks the retained compressed hash, original bytes and unchanged index snapshots before finalizing. Conflicts remain pending for review.

Synthetic tests cover concatenated/empty frames, Unicode split across frames, exact byte equality, damaged streams, bounds/cancellation, pair identity and reference checks, unchanged in-memory SQLite projections, age/activity guards, receipt validation, accounting and inert UI rendering. These tests do not invoke cleanup or native clients. Observed execution and interruption evidence is recorded below; native continuation after deduplication remains unverified.

## Coordinated Codex and Orca hardlinks

History slimming and duplicate cleanup recognize the current user's `~/.codex`, `~/Library/Application Support/Orca/codex-runtime-home/home` and `~/Library/Application Support/Orca/codex-accounts/<UUID>/home`. The Orca application directory name is case-insensitive; discovery returns canonical disk paths so macOS case normalization is not mistaken for a symbolic link. Discovery requires owned directories without symbolic ancestors or group/other write permissions. All discovered homes are scanned for references and included in index and activity checks, even if a home has no alias for the selected history. Root identities and the home set must remain unchanged. This does not extend native whole-session deletion to hardlinked targets.

Only same-relative-path aliases of the same physical inode qualify, with every inode link accounted for and matching metadata. Duplicate cleanup permits one plaintext inode and one same-basename compressed inode. It creates any missing compressed sibling links before removing all plaintext aliases. Slimming stages one replacement inode and atomically replaces each alias with a hardlink to it. Estimates count the original physical bytes once. All original and compressed aliases must be strictly older than 72 hours; no single-target exception applies. An open or uncertain session in any involved home blocks the operation, including during interruption recovery.

Each home's known history databases have separate mandatory projection receipts. Their write transactions are held across the file changes; all databases must commit and pass after-state verification before the original backup is discarded. Shared and standalone history actions re-scan dependencies while their index transactions are held, before mutation or recovery commits, so forks added after the batch scan are not missed. The durable receipt records the alias groups, missing compressed destinations, start state and staged output inode. Partial file replacements or index commits roll forward from verified original/output hashes, exact link counts and recorded identities; conflicts retain the original and pending receipt for review. An interrupted staging file without a recorded output inode can be rebuilt only while every original alias retains its exact metadata and hash, every index retains its before-state, and no backup or replacement link exists. The staging file must be an owned regular file on the original device with one link, bounded size and no added permissions. Success removes the transaction copies and provides no undo.

Read-only synthetic tests cover canonical Orca directory casing, unsafe discovery paths, complete alias accounting, missing compressed siblings, different-basename copies, independent copies, inbound references including forks created after an earlier scan, symbolic links, incomplete scans, strict age/activity guards across homes, receipt identities/lifecycle, every modeled file transition and backup-retention boundary, unjournaled partial staging metadata, physical-byte accounting and file-detail rendering. In-memory SQLite tests cover mixed committed/uncommitted projections converging to the same result while preserving unrelated rows. These tests do not invoke a cleanup planner, preview, executor, recovery probe or native client.

On 2026-11-10, two duplicate-cleanup operations finalized 17 real history pairs across four Codex/Orca homes, removing 23,239,979 logical bytes of plaintext counted once per inode. Complete decoded equality was checked before removal; read-only post-verification confirmed every original alias was absent and every retained compressed alias matched its preview hash. One pair in the first operation required operation-scoped recovery after an uncertain activity check interrupted finalization; recovery verified compressed bytes and recorded index projections before discarding its original transaction backup. The second operation stopped with a `needs-review` receipt. Its one started, unfinished action still had all original and compressed aliases and index projections matching the recorded before-state; no proposed compressed links had been created. The unrelated Claude operation receipt remained unchanged. This covers limited multi-home execution and interruption states, not arbitrary crash recovery, history slimming or native continuation compatibility. Automatic recovery before a new cleanup is restricted to that cleanup's provider.

## Claude tool and skill snapshots: limited native continuation evidence

Read-only inspection on 2026-11-09 compared one transcript written by Claude Code **2.1.296** with the embedded JavaScript in the installed **2.1.319** native executable. The transcript contains 51 records and 330,118 bytes; 26 attachment records account for 314,678 bytes (95.3%). Most of this is prompt/tool snapshots, skill listings and hook context. Inventory totals alone do not establish safe savings.

The [official CLI reference](https://code.claude.com/docs/en/cli-reference) documents that the recorded system prompt is reused across requests, including resume/continue, until compaction; `--system-prompt-snapshot off` instead rebuilds it. The inspected reader selects the latest valid `prompt_snapshot`, restores its system prompt and builds tool-description and tool-schema maps. Repeated descriptions in different fields therefore have distinct consumers. Removing or invalidating the snapshot can fall back to a live prompt, but that changes the replayed context. This static fallback is not proof that an edited transcript completes a native model turn.

Recorded `rendered` content is also used to replay model-facing messages. Without it, the client can reconstruct content from the attachment using its current rendering rules. It is not merely a duplicate display field. The empty display renderer for `prompt_snapshot` does not make it unused: prompt and tool replay consume it separately. Instructions, skill listings and hook output may also contribute context.

In this sample, 25 of the 26 attachment UUIDs are referenced through parent/leaf fields. Deleting whole attachment lines without maintaining the message graph is unsafe. Visible user/assistant text, tool calls and results, thinking/signatures, usage and cost records, timestamps and identity/linkage fields must remain available for historical investigation. The two cost-state records differ and must not be treated as duplicate totals.

A separately authorized native experiment copied this transcript into isolated data roots and working directories. Claude Code **2.1.319**, the existing configured provider and **claude-opus-5-5** completed a real continuation for each variant with `--system-prompt-snapshot on`. The four recall checks enabled only the `Read` tool and disabled live customizations with `--safe-mode`, `--strict-mcp-config` and empty setting sources. These were disposable-copy probes, not cleanup planner, preview or executor runs.

Combined hook compaction cleared `command`, `content`, `stdout`, `stderr` and `rendered` on eight recognized `hook_success` records with `exitCode=0`, saving another **57,573 bytes**. The tagged [rollout wire format](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/history/src/rollout_payload.rs) has no Claude-style request-archive record family.

Codex does have [hook lifecycle events](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/protocol/src/protocol.rs#L1854) containing run status and entries classified as warning, stop, feedback, context or error. ### Older compaction snapshots: limited native continuation evidence

On 2026-11-09, installed Codex CLI **0.167.0** resumed isolated synthetic legacy and paginated histories containing two `compacted` snapshots and messages before, between and after them. Each snapshot contained a distinct marker absent from the ordinary messages. A loopback mock Responses API captured native requests and returned a fixed text response. No real history or authentication data was copied, no paid model was called, and no cc-clean planner, preview or executor was run. Background rollout migration, compression and daemon use were disabled.

In both formats, removing only the older `replacement_history` and its companion `replacement_history_metadata`, while retaining the latest complete snapshot and all other fields, produced **identical initial model input** after normalizing generated message IDs and isolated data-root paths. Both the original and modified histories completed a continuation and completed another continuation after reopening in a new native process. The latest snapshot marker and subsequent messages survived.

Control cases distinguish successful resume from preserved context:

| Modification | Observed native model context in both formats |
| --- | --- |
| Remove only the older history and metadata | Same latest snapshot and subsequent messages as the original. |
| Remove the latest history and metadata | Earlier snapshot, intervening messages and latest textual summary; latest snapshot-only content lost. |
| Remove every history and metadata | Ordinary messages and textual compaction summaries; snapshot-only content lost. |
| Set latest history and metadata to empty arrays | Only messages after the latest snapshot; an empty array is an empty checkpoint, not a request to reconstruct it. |
| Remove latest history but leave its metadata | Latest compaction record, including its summary, absent from reconstructed context. The native wire format rejects metadata without history. |
| Resume a fixture cut off before the second compaction | Removing the first snapshot changes context and loses its unique marker. |

All 22 native runs completed, including four reopen runs. The cutoff fixtures simulate an earlier history boundary; they do **not** test actual fork or rollback APIs. The [reconstruction code](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/session/rollout_reconstruction.rs) explains why the newest surviving complete checkpoint supersedes earlier model context, and why missing history falls back to different reconstruction. The [wire format](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/history/src/rollout_payload.rs) requires history and metadata to remain consistent.

This supports considering superseded snapshots for **continuation from the latest position**, while preserving the latest usable complete snapshot. It does not make deleted snapshots recoverable or establish equivalence for old-position forks, rollbacks, shared histories, encrypted compaction state or other client versions. The mocked endpoint verifies native loading, request construction, response persistence and reopening, not real-model quality or real-provider acceptance.

The approved implementation now enables **Remove old compaction snapshots (Codex)** in Quick clean, offers it unchecked in standalone Slim history, and exposes `--remove-old-snapshots` for CLI cleanup. It removes only `replacement_history` and its companion `replacement_history_metadata` from `compacted` rows before the latest complete checkpoint. It retains the latest row byte-for-byte, including an intentionally empty checkpoint, and preserves row count, ordinals, summaries, usage and all other fields. Each removed snapshot has a separate count and exact byte estimate.

The structural validator follows the known subset of the tagged native wire format, without gating on version strings. It requires a replacement array and numeric window number (including legacy numeric `window_id`) on the latest compaction, validates history items and paired metadata lengths, and retains a file when any compaction is unknown, the latest checkpoint is incomplete or any `thread_rolled_back` event appears. Supported checkpoint state includes retained user/assistant messages and verified answers, guardian history and source metadata, MCP attribution and resource origins, dynamic function/namespace tools, turn attribution and previous-turn settings. Supported response items include message audio, agent messages, additional tools, structured function/custom-tool outputs and internal message metadata with provenance and executed tool calls. Typed objects reject unknown fields and invalid values; open JSON is accepted only where the native schema explicitly uses `serde_json::Value`. Other response shapes, such as tool-search, local-shell and web-search items, remain protected. Cross-rollout references and unknown dependencies also remain protected, alongside age and activity guards.

These extensions follow the `rust-v0.167.0` [response models](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/protocol/src/models.rs), [harness metadata](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/history/src/lib.rs), [retained context](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/history/src/retained_context.rs), [MCP records](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/protocol/src/mcp.rs), [resume metadata](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/history/src/compaction_resume_metadata.rs) and [dynamic tools](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/protocol/src/dynamic_tools.rs). ## Codex native deletion: capabilities and historical 0.167.0 evidence

`src/codex-delete.ts` invokes `codex --no-daemon -c ... delete <uuid> --force` with an argument array. It accepts a full hexadecimal UUID only, requires a canonical absolute directory, fixes `CODEX_HOME`, `CODEX_SQLITE_HOME`, `sqlite_home` and `log_dir`, and runs with that directory as its working directory. Before deletion, `delete --help` must advertise the session argument, force and config options, and `features list` must confirm both background history maintenance features are disabled under the same overrides. Root identity is rechecked between commands. The version string is informational. Native deletion has no shell evaluation, session-name lookup, direct SQLite mutation, or fallback that unlinks rollouts after a native failure.

The tagged command is a thin app-server client. The current adapter explicitly passes `--no-daemon` and rejects inherited `CODEX_EXEC_SERVER_URL` and `CODEX_EXEC_SERVER_NOISE_*` selection. It disables `features.local_thread_store_compression` and `features.background_paginated_rollout_migration` for this invocation, because native startup can otherwise rewrite unrelated rollouts. Configuration may still cause ordinary native startup behavior; this adapter does not promise an entirely network-free child process. Passing capability checks does not establish native compatibility for every version.

Runtime overrides supersede ordinary system, cloud, user, and project configuration. Legacy managed configuration can override them. The adapter conservatively refuses deletion when `/etc/codex/requirements.toml` or `/etc/codex/managed_config.toml` exists, when their absence cannot be established, or when macOS reports a forced `config_toml_base64` / `requirements_toml_base64` preference for `com.openai.codex`. The macOS check queries only the two CoreFoundation presence flags, without copying, decoding, or displaying configuration values. No management policy is removed or bypassed.

Native startup can write outside the selected rollout. Before launching deletion, the adapter checks the root SQLite files and sidecars, `skills/.system`, `tmp`, `.tmp`, `log`, `logs`, `thread-writer-locks`, `sessions`, `archived_sessions`, `installation_id`, `session_index.jsonl`, and `session_index.jsonl.lock`. Symlinks, special files and hardlinks in native maintenance paths are rejected. History hardlinks are checked against the selected ownership scope, so unrelated histories remain usable. The `skills` ancestor is also checked. Ordinary user skill and plugin links outside those paths are allowed. One narrow exception permits native executable aliases at `tmp/arg0-{macos,linux}/codex-arg0*/{apply_patch,applypatch,codex-linux-sandbox}`; those leaf links are not traversed, and native stale-directory cleanup unlinks them. Linked ancestors and lock files remain rejected.

Each child command has a 15-second deadline and a combined 64 KiB output bound. On supported POSIX execution the entire child process group is killed, including a descendant retaining its parent's output pipe. Native stdout/stderr is never included in failure messages. A timeout or error requires reconciliation; it must not trigger an automatic retry or a success receipt.

A fake API key, a loopback-only unreachable API endpoint, and disabled nonessential traffic prevented a model request from being useful; no prompt was submitted. The native resume picker initially displayed both synthetic conversations. After removal of one main JSONL, the picker displayed only the survivor. Native `--resume <surviving-uuid>` rendered its original user text and assistant answer unchanged. Claude Agent SDK 0.3.251 `listSessions` and `getSessionMessages` also reflected the same fixture, but the native picker and transcript rendering are the primary evidence.

This validates listing refresh and reading/resuming the surviving **plain main transcript** after deletion, for 2.1.319. It does not validate a generated continuation, arbitrary signed/tool payload rewriting, unknown attachments, or all subagent layouts. Do not advertise those broader guarantees based on this probe.

The supported cc-clean operation removes only a structurally verified session group: its main JSONL and independently verified uniquely owned subagent/tool-result files. Preserve project memory, configuration, file history, `history.jsonl`, and resources with uncertain ownership. Never substitute `claude purge`: its project/configuration scope is broader than a selected conversation. Malformed or incomplete transcripts, ambiguous references, and unsupported ownership relationships must prevent mutation; version numbers alone do not.
